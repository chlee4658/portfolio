SkincareChart

Charting + Documentation

SkincareChart

Problem
Clinic records, photos, consent documents, payment details, and visit notes were fragmented across disconnected workflows.
Why it mattered
As a physician and clinic operator, I needed charting to reflect how visits, images, forms, products, and payments actually move through a clinic day.
Design decision
I chose a local-first architecture and patient-centered data model so privacy-sensitive files and visit context could stay organized together.
What I built
A clinic charting platform for patient profiles, visits, treatment notes, clinical photos, consent documents, payments, roles, and reporting.
Technologies used
Python, Flask, SQLite, HTML, CSS, JavaScript, Git.
What I learned
Clinical software has to fit the order of work, not just store data. The first system revealed communication gaps around appointments and follow-up.
How it led to the next project
Once charting was structured, appointment reminders and patient communication became the next visible workflow problem.

Skmsg

Messaging Automation

Skmsg

Problem
Appointment communication required repeated manual work across scheduling, reminders, cancellations, and replies.
Why it mattered
After building charting workflows, I saw that scheduling data and communication workflows still lived in separate operational spaces.
Design decision
I integrated calendar events, approved message templates, delivery APIs, inbound replies, and staff confirmation steps into one controlled messaging layer.
What I built
A messaging automation service for appointment reminders, confirmations, cancellation/rescheduling templates, inbound webhook handling, and contact synchronization.
Technologies used
Python, Flask, SQLAlchemy, SQLite/PostgreSQL, Railway, Twilio API, Google Calendar API, Telegram Bot API.
What I learned
Automation in healthcare needs guardrails, templates, logging, and deployment discipline as much as working API integrations.
How it led to the next project
Once messaging was automated, staff needed a faster way to look up context and trigger approved actions during daily operations.
Read project notes
Telegram CRM

Staff Operations

Telegram CRM Bridge

Problem
Staff needed quick operational lookup and controlled messaging without unsafe free-form write actions.
Why it mattered
Operational systems only work if staff can use them quickly without bypassing safety controls or exposing sensitive information.
Design decision
I separated lookup actions from write actions and added approved templates, confirmation gates, audit logs, feature flags, and reversible rollout controls.
What I built
A Telegram-based staff interface for customer lookup, booking lookup, approved-template messaging, confirmations, and controlled workflow execution.
Technologies used
Node.js, TypeScript, Telegram Bot API, HTTP webhooks, feature flags, automated tests.
What I learned
Staff-facing automation requires careful permission boundaries, predictable interaction patterns, and operational fallback paths.
How it led to the next project
This completed the first loop from documentation to communication to staff operations, and shaped my next focus on safer healthcare automation patterns.
